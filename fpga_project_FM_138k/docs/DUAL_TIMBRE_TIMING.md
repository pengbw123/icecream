# 双音色与双流水线的时序取舍

用户本轮关注：增加双音色是否会使时序压力过大。本文件为方案，生产音源仍为32复音单音色。

## 先区分两个限制

- **采样调度**：50 MHz、每1024 clocks输出一个样本。32复音满载实测render=394 clocks，留有调度时间。
- **单拍时序**：20:15版全工程主域Fmax=50.139 MHz，最紧slack=0.056 ns，路径为FFT real_mem输出到band_max使能；ARP扫描、XY峰值统计、FM voice_age写入也有约0.057..0.072 ns的紧路径。即使一个样本很快算完，某一级组合逻辑过长仍会失败。
- 增加音频并行通道不能直接解决FFT/XY/控制路径的时序；后续应先评估这些长路径的流水化余量。

## 三种架构

| 方案 | 调度和时序影响 | 代价 |
|---|---|---|
| 单流水线、32复音、双音色 | 总算子工作量基本不变；增加按part取参数的逻辑，应在取参后寄存，避免接进现有乘法/累加长路径 | 参数和LFO/Pitch EG/踏板按part隔离，改动集中；推荐先做 |
| 两个完整32复音核心，各对应一个音色 | 两核仍各跑50 MHz，各自计算32复音；参数天然隔离。但调度、混音和新增布线也可能产生新关键路径 | 合计64，固定32+32分配；会复制查表ROM和状态存储，RAM紧张 |
| 两条运算通道、动态64声部、声部携带part | 吞吐量高且能动态分配音色的声部配额；参数取数和两通道RAM读写需专门设计 | 最灵活，开发/验证量最大，适合作为后续64复音架构 |

双完整核心的前级分配器方案可行。单音色时同一音色参数写两核，双音色时各核一套，最后按同一个sample_tick对齐、扩位相加，再进**同一条FX链**。实现时应检查引擎现有16位输出是否已限幅，必要时导出更宽的混音值，避免先分别削波再合并。松键/踏板/抢音必须追踪音符所属核心；不能只根据当前音色决定Note Off路由。

固定32+32并不意味着每个音色都能使用64声部。动态64需要将part与运算通道解耦，不能把音色永久绑定某一通道。

RAM是当前更紧的资源：20:15版316/340，仅余24块；DSP65.5/298、逻辑39%。FM综合约22个RAM原语，不能把它直接当作新增物理块数。完整复制一核须先验证能否放下。可共享不可变查表ROM，但两通道需要两读口或明确的分时安排；共享单口ROM不能同时满足两个独立读请求。Delay/Reverb等大缓冲不应随音源核心重复。

## 本轮做的64复音探测

仅在独立testbench中将`TEST_VOICES`设为64，**没有改变生产顶层配置**。

`tb_fm_readback +metrics`：64个声部、65次起音/采样、一次抢音通过，render=**778 clocks**，response=**779 clocks**。778/1024约76%，说明单流水线在该测试场景中已有64复音的计算吞吐潜力。

局限：测试由task逐帧触发，不能据此声称固定1024周期下任意密集事件均不丢样本；没有64复音全工程综合/PnR、全算法PCM验证或实机验收。日志`tmp/check_probe64.log`。这项结果不能替代发布验证。

## 建议顺序

1. 先保持32复音和50 MHz，做LIVE/BACKING两part，完整隔离音色、LFO、Pitch EG、踏板与同音音符所有权。
2. 在参数选择、算法路由选择处设计寄存边界，并将声部号/part/valid对齐；接受少量流水延迟，避免拉长原运算路径。
3. 回归换音色不中断伴奏、两part同音独立松键、满载抢音；以固定1024-clock tick测试密集事件和全部相关deadline。
4. 四域setup/hold TNS=0且主域Fmax>=50 MHz才交付。不能用“样本周期还有空闲”代替单拍时序结果。
5. 双音色稳定后，再根据64复音实际负载和RAM报告决定单通道扩容还是双通道。双流水线可提高吞吐余量，但不是双音色的必要条件。
