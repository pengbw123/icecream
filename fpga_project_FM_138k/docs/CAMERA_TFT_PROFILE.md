# 采用已验证TFT例程的摄像头模式

用户确认第45章`ch45_ov5640_ddr3_tft`可正常出图，而此前本工程QVGA版本仍无图、识别FRAMES始终为0。本轮采用该TFT工程的实际摄像头配置，停止继续调整原QVGA缩放配置。参考工程可出图不等于本工程已经实机验收，最终仍须烧录确认。

## 实际对齐内容

- 完整252项RGB565寄存器写入，与TFT顶层`IMAGE_WIDTH=800`、`IMAGE_HEIGHT=480`、FLIP=0、MIRROR=0的实际展开结果逐项比较，不仅比较少数回读项。PLL/窗口/自动PCLK/ISP均保留原表值，包括3035=21、3036=69、460C=20、5001=83。
- 使用独立`camera_reference_pll`，与TFT顶层实际使用的Gowin_PLL/CLKOUT1一致：50MHz×16÷33，约24.242424MHz。没有采用该工程目录中未实例化的旧camera_pll文件，也不再用HDMI的25MHz作为摄像头XCLK。
- SCCB分频按TFT例程约400kHz设置（50MHz整除得到31个系统时钟/四分之一周期）；硬复位1ms、释放后等20ms、软件复位后等5ms。保留ID/13项模式回读、总线失败重试，摄像头PWDN始终低。
- 生产采集完整800×480，每行1600字节；匹配TFT思路丢弃启动前十帧，本实现还要求这些预热帧格式正确。首批稳定帧宽限10秒，稳定后仍为2秒断流重试。

`tools/check_ov5640_tft_profile.py`直接读取用户提供的TFT ROM/顶层/实际PLL文件，核对252项、尺寸/翻转参数与参考时钟。源文件哈希及比较结果保存在`assets/camera_tft/profile_reference.json`。`src/generated/ov5640_tft_800x480.mem`由`tools/gen_ov5640_config.py`生成，GPRJ和两份CLI清单均已更新。

## 内部数据路径

OV5640的800×480 RGB565流不整体存入RAM。RTL截取中央x=80..719的640×480区域，按4×4取样，输出160×120 RGB332。每帧仍为19200字节，双缓冲容量不增加，不引入DDR或软核图像处理。

这样保持4:3比例，没有采用横向5倍、纵向4倍缩小而压扁手形。HDMI仍显示640×480预览；手势网络仍读同一份160×120采样流的中央96×96区域。屏幕识别框对应原始800×480画面的中央384×384区域，避免改动网络的输入形状、权重和门限。

摄像头初始化/采集/NN复位以摄像头参考PLL为准，HDMI失锁只撤销显示缓冲和输出，不重新初始化摄像头，也不停止NN。摄像头PLL失锁则异步清除摄像头与NN状态，各域再同步释放复位。

## 时序与资源边界

- HDMI仍为25/125MHz，RGB菜单及音频时钟不变。
- 独立参考PLL的24.242MHz生成时钟已明确约束；外部PCLK预算提高到85MHz，而非沿用旧50MHz。原先下降沿发射、上升沿采样的0.5～5ns输入延迟预算保持不变，没有用放宽输入延迟来规避更高速率。
- 85MHz是本轮实现的时序预算，不是已实测的传感器速率；实际PCLK仍须用诊断P核对。多用一个PLL，帧缓存尺寸、UI固件和NN参数不增加。

## 诊断的正常值

识别关闭时保留四行相机诊断，全部为十六进制：

| 字段 | 800×480模式下的正常含义 |
|---|---|
| ID/E/READY | 5640/0/1；只证明配置通过 |
| P | 实测PCLK，单位kHz；须在85MHz预算内，不能照旧版10MHz预期判断 |
| R | 01E0，即480行 |
| B | 0640-0640，每行1600字节 |
| N | 4B00，即裁剪/降采样后19200像素 |
| F | 收到完整帧快照后00；初始00不代表已成功 |
| S | 十帧预热完成后通常E8～EB，低两位是瞬时H/V |
| G | 显示的完整帧数开始变化，允许整帧丢弃 |

烧录后先等约12秒观察以上数据，再只开RECOGNITION、保持CONTROL关闭，确认RGB手势页FRAMES持续增加。只有这一步通过，才能继续评价实拍分类效果。
